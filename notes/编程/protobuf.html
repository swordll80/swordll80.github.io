Protocol Buffers 手册

16 条
Protocol Buffers (Protobuf) 是 Google 的语言/平台无关、可扩展的结构化数据序列化机制：用 .proto 定义结构，protoc 生成多语言代码，二进制紧凑高效，常配 gRPC。
1 是什么
用 .proto 文件定义消息结构 → protoc 编译生成目标语言类 → 代码里序列化/反序列化。 特点：二进制紧凑、快、跨语言、向后/向前兼容。 对比 JSON/XML：更小更快但不可读，需 schema。
2 proto2 与 proto3
文件首行声明 syntax = "proto3";(推荐) 或 "proto2";。 proto3 简化：默认无 required、标量有默认值、去掉部分特性； proto3 也支持 optional(区分“未设置”)。
3 编译命令
protoc --proto_path=. --cpp_out=. --python_out=. foo.proto 生成 C++/Python/Java/Go 等；gRPC 用 --grpc_out + 插件。
4 基本 message
syntax = "proto3"; package demo; message Person { string name = 1; int32 age = 2; repeated string roles = 3; } 每个字段有唯一字段号(field number)，编码时用它而非名字。
5 字段规则
singular：0或1个(proto3 默认)。 optional：显式可选，可判断是否设置。 repeated：0或多个(数组/列表)。 字段号 1–15 占 1 字节(高频字段优先用)，16–2047 占 2 字节。
6 字段号规则
字段号一旦发布不可更改/复用；删除字段用 reserved 保留号与名： reserved 2, 15, 9 to 11; reserved "foo", "bar"; 以保证向后兼容、防止误用。
7 标量类型
整数：int32 int64 uint32 uint64 zigzag(负数高效)：sint32 sint64 定长：fixed32 fixed64 sfixed32 sfixed64 浮点：float double 布尔：bool 字符串：string(UTF-8) 字节：bytes 默认值：数值0、bool false、string ""、枚举首项。
8 枚举 enum
enum Status { UNKNOWN = 0; // proto3 首项必须为0 ACTIVE = 1; CLOSED = 2; } 未知枚举值在解码时保留(前向兼容)。
9 嵌套 / oneof / map
message 可嵌套定义；引用其它 message 作字段类型。 oneof：多字段互斥，只存其一(节省空间)。 map<string, int32> scores = 4; 键值对。
10 字段键 Tag
每个字段前缀一个 key = (field_number << 3) | wire_type。 wire_type：0=Varint, 1=64-bit, 2=Length-delimited, 5=32-bit(3/4 已弃用)。 key 本身以 varint 编码。
11 Varint
变长整数：每字节低7位存数据，最高位(MSB)=1 表示后续还有字节，小端顺序。 小数值占 1 字节，非常省空间。 如 300 = 0xAC 0x02。
12 ZigZag
有符号数直接 varint 会让负数很大(占10字节)。 sint32/sint64 用 zigzag 映射：0→0, -1→1, 1→2, -2→3 … 公式：(n << 1) ^ (n >> 31)。
13 长度分隔与解码
wire_type 2 (string/bytes/嵌套 message/packed repeated)：key 后跟 varint 长度再跟内容。 未知字段按 wire_type 跳过 → 前后兼容。 调试：protoc --decode_raw < data.bin 或 protoscope。
14 gRPC 服务定义
service Greeter { rpc SayHello (HelloRequest) returns (HelloReply); rpc Stream (Req) returns (stream Reply); // 流式 } 结合 HTTP/2，支持一元/服务端流/客户端流/双向流。
15 兼容性最佳实践
只增不改：新增字段用新字段号；不改已用字段号/类型语义。 删除字段→reserved；用 optional/默认值平滑演进。 枚举保留 0 值为默认/未知。
16 与其它格式对比
Protobuf：需 schema、二进制、最快最小，适合内部 RPC/存储。 JSON：可读、免 schema、体积大。 FlatBuffers/Cap'n Proto：零拷贝，读极快。 Avro/Thrift：类似定位，各有生态。
